# 작업 규칙 (AGENTS.md)

이 저장소의 모든 Codex 세션이 따르는 규칙이다. 방향과 최종 판단은 사용자가, 실행과 검증은 Codex가 맡는다.

## 0. 세션을 시작할 때
1. `notes/HANDOFF.md`에 인계 내용이 있으면 먼저 읽고, 현재 상태를 3줄로 요약한 뒤 이어서 진행한다.
2. `notes/PROBLEM.md`의 성공 기준이 비어 있으면 코드를 쓰기 전에 `$kickoff`부터 진행한다.

## 1. 절대 규칙
- `git push`, 원격 저장소 추가, 외부 업로드를 하지 않는다.
- 과제 문제·데이터·코드·결과물을 외부로 보내지 않는다. 공유 링크, 붙여넣기 사이트, 외부 API 전송 모두 해당한다.
- Codex와 과제가 제공한 모델·API 외의 AI 모델이나 서비스를 호출하거나 연결하지 않는다. 산출물에 외부 사전학습 모델이나 외부 API가 필요해 보이면 먼저 사용자에게 묻는다.
- 화면·브라우저 자동 조작 도구(computer use, Playwright, Selenium, Puppeteer, xdotool 등)를 쓰지 않는다. 웹 기능은 테스트 코드나 HTTP 요청으로 검증한다.
- 샌드박스·네트워크·프록시·감독·보안 설정을 바꾸거나 우회하지 않는다. 막히면 멈추고 사용자에게 알린다.
- 웹 검색은 일반 기술 질문에만 쓰고, 과제 원문이나 데이터를 검색어에 넣지 않는다.
- 공개 코드·알고리즘은 일부만 참고하고 출처를 `notes/DECISIONS.md`에 남긴다. 결과물을 통째로 가져오지 않는다.
- 공개 패키지 설치(pip, npm 등)는 해도 된다. 설치한 것은 의존성 파일에 기록한다.

## 2. 일하는 방식
- **성공 기준이 범위다.** `notes/PROBLEM.md`의 성공 기준과 연결되지 않는 기능은 만들지 않는다. 범위를 넓히려면 먼저 묻는다.
- **요구가 바뀌면 문서부터.** `notes/PROBLEM.md`와 `notes/PLAN.md`를 먼저 고치고(변경 이력에 이유), 그다음 코드를 바꾼다.
- **작게, 끝까지.** `notes/PLAN.md`의 단계를 하나씩 진행하고, 각 단계는 구현 → 검증 → 커밋으로 끝낸다. 동작하는 최소 버전(E2E)을 먼저 만들고 다듬는다.
- **판정은 코드로.** 계산·판정·규칙은 결정론적 코드로 고정하고, LLM은 해석·요약·초안에만 쓴다.
- **모호하면 기본안과 함께 묻는다.** 질문은 한 번에 3개 이하로, 답이 없을 때 적용할 기본안을 같이 적는다.
- **같은 실패 두 번이면 멈춘다.** 시도를 더 쌓지 말고 원인 가설과 선택지를 보고한다.
- **시간을 본다.** 시작 시각은 `notes/PLAN.md`에 있다. 단계가 끝날 때마다 `date`로 경과 시간을 확인하고, 늦어지면 범위 축소안을 먼저 낸다. 시작 후 160분부터는 `$wrap-up`만 한다.

## 3. 검증
- 실행 증거(명령과 결과) 없이 "완료"라고 말하지 않는다.
- 단계를 마치기 전에 `bash .agents/skills/verify/scripts/check.sh`를 실행한다. 결과는 `notes/VERIFY.md`에 자동으로 남는다.
- 핵심 로직에는 테스트를 둔다: 정상 1개 + 경계·예외 1~2개. 테스트를 통과시키려고 기대값을 바꾸지 않는다.
- 데이터·ML 작업은 시드 고정, 학습/검증 분리, 단순 기준선 비교, 지표와 측정 방법 기록을 지킨다.

## 4. 기록 (짧게, 사실만)
| 파일 | 내용 |
|---|---|
| `notes/PROBLEM.md` | 문제, 성공 기준(검증 방법 포함), 범위, 제약, 가정, 인터뷰 요약 |
| `notes/PLAN.md` | 시작 시각, 단계별 완료 조건·검증 방법·담당·상태·커밋, 변경 이력 |
| `notes/DECISIONS.md` | 결정 로그, 리스크 목록(약점 → 영향 → 탐지 → 대응), 참고 자료 출처 |
| `notes/VERIFY.md` | 검증 로그(check.sh 자동 기록 + 성공 기준 대조) |
| `notes/REVIEW.md` | 교차검증 발견 사항과 처리 결과 |
| `notes/HANDOFF.md` | 세션 인계 |

문서와 실제 코드·커밋은 항상 일치해야 한다. 코드를 바꿨으면 관련 문서도 같은 커밋에서 고친다.

## 5. 커밋
- 단계마다 커밋한다. 메시지는 `<type>: <무엇을, 왜>` (type: feat, fix, test, refactor, docs, chore). 검증했으면 끝에 `(verified: <핵심 증거>)`를 붙인다.
- `git status --short`로 확인하고 의도한 파일만 add 한다. 비밀키, `.env`, 대용량 산출물, 가상환경은 커밋하지 않는다.
- push는 하지 않는다.

## 6. 보고 (한국어, 짧게)
- 사용자가 판단해야 할 것을 맨 위에 둔다.
- 그다음 바뀐 것(파일) / 검증(명령 → 결과) / 다음 할 일 / 위험 신호 순서로 쓴다.

## 7. 스킬
| 스킬 | 언제 |
|---|---|
| `$kickoff` | 시작 직후: 정찰, 인터뷰 질문, 문제 정의, 계획 |
| `$verify` | 단계마다: 자동 점검, 테스트, 실제 실행, 성공 기준 대조, 커밋 |
| `$cross-check` | 마일스톤 후·제출 전: 새 세션에서 독립 리뷰(코드 수정 없이 기록만) |
| `$explain` | 큰 기능 후·마무리 전: 구조·결정·리스크 정리, 사용자 브리핑 |
| `$handoff` | 맥락이 길어질 때: 인계 문서 작성 후 새 세션 |
| `$wrap-up` | 시작 후 160분: 기능 동결, 최종 검증, README, 최종 커밋 |

## 8. 문서 조회
OpenAI API·SDK·Codex 관련 내용은 `openaiDeveloperDocs` MCP로 최신 문서를 먼저 확인하고, 근거 페이지를 `notes/DECISIONS.md`에 남긴다. MCP가 연결되지 않았으면 공식 문서를 웹 검색한다.
