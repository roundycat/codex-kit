# 작업 규칙

이 저장소에서 일하는 모든 Codex 세션이 따르는 규칙이다. 사용자가 방향과 최종 판단을 맡고, Codex는 실행·검증·기록을 맡는다.
과제 설명과 주최 측 안내는 이 문서보다 우선한다. 단, 1절의 시험 규칙은 어떤 경우에도 지키며, 둘이 충돌해 보이면 멈추고 사용자에게 묻는다.

## 1. 시험 규칙 (예외 없음)
- **밖으로 내보내지 않는다.** `git push`, 원격 저장소 추가, 파일 업로드, 공유 링크, 붙여넣기 사이트 등 과제의 문제·데이터·코드·결과물이 외부로 나가는 일은 하지 않는다.
- **AI는 제공된 Codex만 쓴다.** 다른 AI 모델·서비스·에이전트를 호출하거나 연결하지 않고, 이미지 생성(`imagegen`) 같은 별도 AI 기능도 쓰지 않는다. 과제가 결과물용으로 제공한 모델·API는 안내대로 쓰고, 그 밖의 외부 모델·API가 필요해 보이면 구현 전에 사용자에게 묻는다.
- **모델을 바꾸지 않는다.** 모델 변경을 제안하지 않는다. Astra 계열(이름에 `astra`가 들어간 모델)은 주최 측이 제한한 모델이므로 어떤 경우에도 쓰지 않는다. 하위 에이전트는 스킬이 지시할 때만 띄우고 `model`·`reasoning_effort`를 지정하지 않는다.
- **화면·브라우저를 자동 조작하지 않는다.** computer use, Playwright, Selenium, Puppeteer, xdotool 같은 도구는 설치하지도 실행하지도 않는다. 웹 기능은 단위 테스트와 HTTP 요청(curl, 테스트 클라이언트)으로 검증한다.
- **제한을 우회하지 않는다.** 샌드박스·승인·네트워크·프록시·감독·보안 설정을 설정 파일, 실행 플래그, 환경 변수로 바꾸지 않는다. 설치나 다운로드가 막혀도 다른 미러나 프록시로 돌아가지 않는다. Codex의 승인 요청을 사용자가 허락하는 것은 정상 절차이고, 그 밖의 방법이 필요하면 멈추고 알린다.
- **검색어에 과제를 넣지 않는다.** 웹 검색과 문서 MCP에는 일반 기술 질문만 넣는다. 과제 원문, 데이터, 고유 명칭은 넣지 않는다.
- **외부 코드는 일부만 참고한다.** 참고한 공개 코드·알고리즘은 출처와 반영 위치를 `notes/DECISIONS.md`에 적고, 결과물을 통째로 가져오지 않는다. 공개 패키지 설치는 허용되며 설치한 패키지는 의존성 파일에 적는다.

## 2. 누가 정하나
- **사용자가 정한다:** 요구사항 해석과 성공 기준, 범위 확대·축소, 되돌리기 어려운 선택(전체 구조, 데이터 모델, 무거운 의존성, 알고리즘·모델 선택), 파일과 기록 삭제. 이때는 선택지 2~3개와 추천안, 이유를 짧게 내고 답을 기다린다. 답과 무관한 작업은 그동안 계속한다.
- **Codex가 정한다:** 그 밖의 구현 세부(이름, 파일 배치, 라이브러리 사용법, 테스트 구성)는 묻지 않고 진행하고, 결정과 이유를 보고에 한 줄씩 남긴다.
- **질문은 한 번에 3개 이하로** 하고, 각 질문에 답이 없을 때 적용할 기본안을 붙인다. 실무자에게 보낼 질문 초안은 이 제한에서 뺀다.
- **실무자(이해관계자 AI)는 플랫폼의 별도 채팅창에 있고, Codex는 그 대화를 볼 수 없다.** 실무자에게 물을 것은 질문 초안으로 사용자에게 준다. 사용자가 전한 답만 `notes/PROBLEM.md` 인터뷰 기록에 적고 답을 지어내지 않는다. 확인하지 못한 내용은 가정으로 적고 진행한다.
- 사용자가 예상이나 우려를 말했으면 결과와 대조해 맞았는지 보고한다.

## 3. 진행 방식
- **세션 시작:** `notes/HANDOFF.md`에 인계 내용이 있으면 읽고 현재 상태를 3줄로 요약한 뒤 사용자의 이번 요청을 따른다. 인계 시점 커밋이 현재 HEAD와 다르면 `git log`로 그 사이 변경을 확인한다. `notes/PROBLEM.md`의 요구사항이 비어 있는데 구현을 요청받으면 `$kickoff`를 먼저 진행한다(사용자가 건너뛰라고 하면 따른다).
- **범위:** `notes/PROBLEM.md`의 요구사항(R: 과제가 명시한 요구와 제출 조건, 빠짐없이)과 성공 기준(S: 측정 가능한 기준 3~5개)에 연결되지 않는 기능은 만들지 않는다.
- **요구가 바뀌면 문서부터:** 새 요구나 실무자의 답이 오면 `notes/PROBLEM.md`와 `notes/PLAN.md`(변경 이력에 이유)를 먼저 고친 뒤 코드를 바꾼다.
- **작게, 끝까지:** `notes/PLAN.md`의 단계를 하나씩 진행한다. 끝에서 끝까지 동작하는 최소 버전을 먼저 만들고, 위험한 부분은 앞 단계에서 확인한다. 각 단계는 구현 → 검증 → 커밋으로 끝낸다.
- **판정은 코드로:** 과제가 달리 요구하지 않으면 계산·판정·규칙은 결정론적 코드로 둔다. 결과물에 LLM을 쓰면 출력을 스키마로 검증하고 실패 시 대체 동작을 둔다.
- **같은 실패를 반복하지 않는다:** 같은 오류가 두 번 나면 세 번째로 같은 시도를 하지 않는다. 원인 가설과 다음 선택지를 보고하고 사용자가 고르게 한다.
- **시간:** 플랫폼 타이머 기준 종료 시각과 마무리 시작 시각(종료 20분 전)은 `notes/PLAN.md`에 있다. 현재 시각은 `TZ=KST-9 date +%H:%M`(한국 시간)으로 확인한다. 단계를 마칠 때마다 남은 시간을 보고하고, 계획보다 늦으면 범위 축소안을 먼저 낸다. 마무리 시작 시각부터는 `$wrap-up`만 한다.

## 4. 완료의 기준
다음 네 가지를 갖춰야 "완료"라고 말한다.
1. `bash .agents/skills/verify/scripts/check.sh` 결과에 FAIL이 없다. 결과는 `notes/VERIFY.md`에 자동으로 쌓인다.
2. 핵심 경로를 실제로 실행해 확인했다(명령과 출력).
3. 관련 R·S의 충족 여부와 증거를 `notes/VERIFY.md`에 적고 `notes/PROBLEM.md`의 상태를 갱신했다.
4. 커밋했다.

- 테스트는 요구사항을 판정하도록 쓴다. 핵심 로직마다 정상 1개와 경계·예외 1~2개를 두고, 구현을 그대로 베낀 테스트는 쓰지 않는다.
- 테스트를 통과시키려고 기대값을 바꾸거나 테스트를 건너뛰게 하지 않는다. 기대값이 틀려 보이면 근거와 함께 보고한다.
- `check.sh`가 잘못 판정한다고 보이면 스크립트를 고치지 말고 근거와 함께 보고한다.
- 데이터·ML: 시드 고정, 학습/검증 분리, 단순 기준선 비교, 지표와 측정 방법 기록. 오래 걸리는 작업은 작은 표본으로 시간을 먼저 잰다. 수치는 실제 실행 결과만 쓴다.
- 서버처럼 계속 도는 프로세스는 백그라운드로 띄워 로그와 PID를 남기고, 확인이 끝나면 종료한다.

## 5. 기록
| 파일 | 내용 |
|---|---|
| `notes/PROBLEM.md` | 요구사항(R), 성공 기준(S)과 검증 방법·상태, 범위, 가정, 실무자 인터뷰 |
| `notes/PLAN.md` | 종료·마무리 시각, 단계별 관련 R·S·완료 조건·검증·담당·상태, 변경 이력 |
| `notes/DECISIONS.md` | 결정 로그, 리스크(어디가 → 왜 위험한가 → 어떻게 알아채나 → 대응), 참고 자료 |
| `notes/VERIFY.md` | check.sh 자동 기록, R·S 대조 결과 |
| `notes/REVIEW.md` | 독립 리뷰 발견 사항과 처리 결과 |
| `notes/HANDOFF.md` | 세션 인계 |

- 확인한 사실만 짧게 쓴다. 코드를 바꾸면 관련 기록도 같은 커밋에서 고친다.
- 기록을 지우지 않는다. 커밋 기록과 과제가 준 파일은 평가와 인계의 근거다. `commit --amend`, rebase, `reset --hard`, `stash`, `clean`, 파일 삭제는 사용자가 요청할 때만 한다.
- 이 규칙 블록과 `.agents/skills/`는 사용자가 요청할 때만 고친다. 아래 "이 저장소" 절은 Codex가 최신으로 유지한다.

## 6. 커밋
- 검증을 마친 단계마다 커밋한다. 이 규칙이 커밋 허락이다. push는 하지 않는다.
- 메시지는 `<type>: <무엇을, 왜>` (feat, fix, test, refactor, docs, chore). 계획 단계의 작업이면 단계 번호를, 검증했으면 끝에 `(verified: <핵심 증거>)`를 넣는다. 예: `feat: 2단계 결측 행 처리 추가, R3 충족 (verified: pytest 6 passed)`
- `git status --short`로 확인하고 의도한 파일만 add 한다. 비밀값, `.env`, 대용량 산출물, 가상환경, 캐시는 커밋하지 않고, 비밀값은 출력이나 보고에도 쓰지 않는다.

## 7. 보고
- 한국어로 짧게 쓴다. 사용자가 판단할 것이 있으면 맨 위에 둔다.
- 그다음 바뀐 것(파일), 검증(명령 → 결과), 남은 시간과 다음 할 일, 위험 신호를 쓴다.
- 설계 결정에는 이유를 한 문장 붙인다. 사용자가 자기 말로 설명할 수 있어야 한다.

## 8. 스킬과 문서
| 스킬 | 언제 |
|---|---|
| `$kickoff` | 과제 시작 직후: 종료 시각, 정찰, 실무자 질문, R·S, 계획 |
| `$verify` | 단계를 마칠 때마다: 자동 점검, 실제 실행, R·S 대조, 커밋 |
| `$cross-check` | 첫 E2E가 돈 뒤, 늦어도 종료 50분 전: 독립 리뷰(코드 수정 없이 기록만) |
| `$explain` | 큰 기능을 마친 뒤, 늦어도 종료 30분 전: 구조·결정·리스크 정리와 브리핑 |
| `$handoff` | 대화가 길어졌을 때: 인계 문서를 쓰고 `/new` |
| `$wrap-up` | 마무리 시작 시각(종료 20분 전): 기능 동결, R 대조, 최종 검증, README, 최종 커밋 |

OpenAI API·SDK·Codex에 관한 내용은 `openaiDeveloperDocs` MCP나 내장 `openai-docs` 스킬로 공식 문서를 확인하고, 근거를 `notes/DECISIONS.md`에 남긴다.
