# cross-check: 독립 리뷰

목적: 만든 쪽의 기억에 기대지 않고 파일과 실행 결과만으로 다시 검증한다.

## 누가 리뷰하나
- **지금까지 코드를 만든 세션이라면**: 하위 에이전트를 띄울 수 있으면(`spawn_agent`) 리뷰를 맡긴다. 대화 맥락을 넘기지 않고(`fork_turns: "none"`), `model`과 `reasoning_effort`는 지정하지 않는다. 맡길 메시지: "`.agents/skills/cross-check/SKILL.md`의 '리뷰 절차'를 그대로 수행하라. 코드는 고치지 말고 `notes/REVIEW.md`와 `/tmp`에만 쓰고, 커밋하지 마라. 끝나면 H·M 항목을 요약해 답하라." 끝날 때까지 기다린 뒤 '리뷰 후 처리'로 간다.
  하위 에이전트를 쓸 수 없으면 사용자에게 `$handoff` → `/new` → `$cross-check` 순서를 안내하고 멈춘다.
- **새 세션이거나 리뷰를 맡은 하위 에이전트라면**: 아래 리뷰 절차를 직접 수행한다.

## 리뷰 절차
1. **읽기**: `AGENTS.md`, `notes/PROBLEM.md`(R·S), `notes/PLAN.md`, `notes/REVIEW.md`(이전 리뷰), `git log --oneline -20`, 이전 리뷰 이후의 변경(`git diff <기준 커밋>..HEAD --stat`으로 범위를 본 뒤 핵심 파일).
2. **점검** (중요한 순서대로):
   - 요구사항: R마다 구현과 증거가 있는가? 제출 조건(파일, 위치, 형식, 실행 방법)을 지키는가? 문서와 코드·커밋이 일치하는가?
   - 정확성: 빈 입력, 잘못된 입력, 경계값, 단위와 타입, 오프바이원, 예외 처리.
   - 데이터·ML(해당 시): 데이터 누수, 학습/검증 분리, 시드, 기준선 대비 성능, 지표의 타당성.
   - 보안·운영: 하드코딩된 비밀값, 입력 검증, 민감정보 로그, 외부 호출 실패 시 동작.
   - 과잉 구현: R·S와 무관한 기능, 불필요한 복잡도.
3. **직접 확인**: 의심 지점은 실행해서 확인한다(테스트 실행, `/tmp`의 작은 재현 스크립트).
4. **기록**: `notes/REVIEW.md`에 리뷰 시각(`TZ=KST-9 date +%H:%M`)과 기준 커밋을 적고, 발견 사항을 심각도순으로 쓴다.
   `[H|M|L] 파일:줄 — 문제 / 근거(재현 명령이나 코드) / 제안`
5. **보고**: H 항목부터 한 줄씩 쓰고 "지금 고칠 것 / 미룰 것"을 추천한다.

## 리뷰 후 처리 (만든 세션)
추천안을 사용자에게 보여 주고 고칠 범위를 확인받는다. 고친 항목 옆에 처리 결과(커밋 해시 또는 미룬 이유)를 적고 `$verify`로 확인한다.
