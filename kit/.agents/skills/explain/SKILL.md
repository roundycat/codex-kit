# explain: 내가 설명할 수 있게

사용자가 AI 없이 이 산출물을 설명할 수 있어야 한다. 추측하지 말고 실제 코드를 읽어 근거(파일:줄)를 단다.

1. **구조**: 진입점 → 핵심 모듈 → 데이터 흐름을 5~8줄로 쓴다. 각 줄에 파일 경로를 붙인다.
2. **결정**: `notes/DECISIONS.md`의 결정 로그를 코드와 대조해 빠진 결정을 채운다.
   결정 / 이유 / 버린 대안과 버린 이유 / 트레이드오프
3. **리스크 목록 (가장 중요)**: 약한 곳 3~6개를 찾아 리스크 표에 추가하거나 갱신한다. 각 항목은 이 순서를 지킨다.
   - 어디가: 파일:줄, 어떤 조건에서
   - 왜 위험한가: 터지면 누구에게 어떤 영향이 있나
   - 어떻게 알아채나: 증상, 로그, 테스트
   - 대응과 다음 검증: 즉시 대응, 근본 수정, 추가할 테스트

   살펴볼 후보: 입력 규모 급증, 외부 API 실패·지연, 결측·이상치, 성능 저하, 동시 요청, 잘못된 설정, 데이터 분포 변화.
4. **숫자**: 성능 지표나 처리 시간이 있으면 실제 측정값과 측정 방법을 적는다. 추정하지 않는다.
5. **브리핑**: 사용자에게 각 1~2문장으로 준다.
   무엇을 왜 만들었나 / 핵심 동작 원리 / 가장 큰 약점 2개와 대응 / 시간이 더 있으면 할 일
6. **커밋**: `git add notes && git commit -m "docs: update decisions and risks"` (push 금지)
