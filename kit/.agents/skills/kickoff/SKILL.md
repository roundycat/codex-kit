# kickoff: 문제 정의와 계획

목표: 코드를 쓰기 전에 "무엇이 성공인가"를 측정 가능하게 정하고, 작업을 검증 가능한 단계로 쪼갠다. 이 스킬을 진행하는 동안에는 코드를 수정하지 않는다.

## 1. 정찰 (읽기만, 5분 안에)
1. `date`로 현재 시각을 확인하고 `notes/PLAN.md`의 시작 시각과 마무리 시작 시각(시작 + 160분)에 적는다.
2. 저장소를 훑는다: `git log --oneline -5`, 최상위 파일 목록, README와 과제 설명, 데이터 파일, 기존 코드와 테스트.
3. 데이터가 있으면 크기, 컬럼, 앞부분 몇 줄, 결측·이상치만 요약한다. 전체를 출력하지 않는다.
4. 실행 환경을 확인한다: 언어와 버전, 설치된 패키지, 실행·테스트 명령.

## 2. 요약과 질문
사용자에게 짧게 보고한다.
- 과제 한 줄 요약: 누가, 무엇 때문에, 무엇을 원하나
- 과제 설명에 이미 명시된 요구사항, 그리고 비어 있거나 모호한 부분
- 실무자에게 물을 질문 5~7개를 우선순위순으로. 해법 단어(AI, 자동화, 대시보드 등)를 피하고 문제 자체를 묻는다.
  1. 최근에 이 문제가 실제로 생긴 구체적 사례
  2. 지금의 우회 방법과 그 비용(시간, 돈, 실수)
  3. 빈도, 규모, 현재 수치
  4. 누가 쓰고 누가 결과를 받는지
  5. 이번에 안 해도 되는 것, 절대 틀리면 안 되는 것
  6. 무엇을 보면 "됐다"고 판단할지

과제 설명에 이미 답이 있는 질문은 빼거나 확인용 질문으로 바꾼다.

## 3. 문제 정의서
사용자가 인터뷰 답(또는 "가정으로 진행")을 주면 `notes/PROBLEM.md`를 채운다.
- 성공 기준은 3~5개. 각 기준은 측정 가능해야 하고 검증 방법(명령, 테스트, 수치)을 갖는다.
- 만들 것과 만들지 않을 것을 나눠 범위를 좁힌다.
- 확인되지 않은 내용은 근거와 함께 "가정"에 적는다.
- 인터뷰 기록은 질문과 답의 핵심만 남긴다.

그다음 사용자가 실무자에게 보낼 3~5줄짜리 확인 메시지(이해한 문제, 성공 기준, 만들지 않을 것)를 만들어 준다.

## 4. 계획
`notes/PLAN.md`에 단계를 쓴다.
- 1단계는 끝에서 끝까지 동작하는 최소 버전(E2E v0)이다.
- 각 단계는 30분 이하이고, 완료 조건과 검증 방법을 갖는다.
- 위험이 큰 부분(데이터 품질, 외부 의존, 성능)은 앞 단계에서 먼저 확인한다.
- 담당 열에 Codex가 실행할 일과 사용자가 판단할 일을 구분해 적는다.
- 마지막 20분은 `$wrap-up` 몫으로 비워 둔다.

## 5. 마무리
`git add notes && git commit -m "docs: define problem, success criteria and plan"` (push 금지)

사용자에게 보고한다: 성공 기준 목록, 첫 3단계, 사용자가 확인해야 할 것.
